# 리팩토링 가이드

## 패턴의 본질

디자인 패턴에서 가장 중요한 것은 **기술 자체가 아니라 의도**다.

어떤 패턴을 "어떻게 구현했는가"보다 중요한 것은
**왜 이 패턴이 필요했고, 어떤 문제를 해결하기 위해 선택했는가**이다.

패턴을 단순한 공식처럼 적용하면 오히려 구조가 경직되고 유연성이 떨어져 유지보수가 어려워질 수 있다.
결국 패턴은 **프로젝트의 맥락과 문제를 이해한 상태에서 선택되어야 한다**.

---

## 오버엔지니어링에 대한 생각

모든 상황에 디자인 패턴을 적용하려는 태도는 피하는 것이 좋다.

패턴에 대한 과도한 집착은 다음과 같은 문제로 이어질 수 있다:

- 개발 속도 저하
- 가독성 악화
- 유지보수 비용 증가
- 구조 변경의 어려움

따라서 **필요한 곳에, 필요한 수준으로만 패턴을 적용하는 것이 이상적**이다.

---

## 로직 분리가 필요한 이유

| 문제         | 증상                       | 예시                                   |
| ------------ | -------------------------- | -------------------------------------- |
| **가독성**   | 전체 흐름 파악이 어려움    | 한 파일이 300줄 이상                   |
| **재사용성** | 유사 코드의 반복           | 다른 컴포넌트에서 동일 로직 복사       |
| **테스트**   | 로직 단위 테스트 불가      | UI와 비즈니스 로직이 결합됨            |
| **유지보수** | 수정 영향 범위 예측 어려움 | 한 수정이 다른 버그 유발               |
| **협업**     | 충돌 빈번할 것으로 예상    | 동일 파일 수정으로 merge conflict 발생 |

이 문제들은 단순 코드 스타일의 문제가 아니라 **구조적 설계 문제**라고 판단했다.

---

## 디자인 패턴 적용 전 자문 기준

1. **지금 어떤 문제가 있는가?** → 문제가 없다면 패턴은 필요 없다
2. **이 패턴이 그 문제를 해결하는가?** → 해결하지 못한다면 다른 접근을 고려
3. **패턴 적용 비용보다 얻는 이점이 큰가?** → 비용이 더 크다면 적용하지 않는다
4. **팀원(또는 미래의 내가) 이해할 수 있는 구조인가?** → 나만 이해하는 구조는 리스크

**디자인 패턴은 "How"보다 "Why"와 "When"을 중심으로 선택해야 한다.**

---

## 프로젝트 적용 방향

- 최신 트렌드(FSD, Atomic Design 등)는 참고하되, 이번 프로젝트에서는 채택하지 않음(오버엔지니어링)
- 포트폴리오 목적에 맞게 **대중적이고 현업 친화적인 구조** 선택
- 뷰(UI)와 비즈니스 로직을 분리하여 **가독성과 재사용성** 우선

---

## 현재 프로젝트 아키텍처

### 적용한 패턴

| 패턴                        | 설명                                    |
| --------------------------- | --------------------------------------- |
| **Layered Architecture**    | API → Hooks → Components 계층 분리      |
| **Feature-based Structure** | 도메인(post, comment 등) 기준 폴더 구성 |
| **Colocation**              | 관련 로직을 가능한 한 가까이 배치       |

### 레이어 구조

```
┌───────────────────────────────────┐
│ Pages (페이지 로직 + 조합)        │
├───────────────────────────────────┤
│ Components (UI + 컴포넌트 로직)   │
├───────────────────────────────────┤
│ Hooks (서버 상태 + 유스케이스)    │  ← queries / mutations
├───────────────────────────────────┤
│ Store (클라이언트 전역 상태)      │  ← Zustand
├───────────────────────────────────┤
│ API (Supabase 호출 - 순수 함수)   │
└───────────────────────────────────┘
```

---

## 폴더 구조

```
src/
├── pages/        # 페이지 단위 컴포넌트 (페이지 로직 + 조합)
├── components/   # UI 컴포넌트 (post/, comment/, profile/)
├── hooks/        # 서버 상태 관리 (queries/, mutations/)
├── store/        # 전역 클라이언트 상태 (Zustand)
├── api/          # 외부 API 통신 (Supabase)
└── lib/          # 공통 유틸리티
```

### 데이터 흐름

```
Pages → Components → Hooks → API
                  ↘ Store
```

### 설계 원칙

- **단방향 의존성** 유지
- **관심사 분리** (UI / 서버 상태 / 클라이언트 상태 / API)
- **기능 단위 구조화**로 확장성과 가독성 확보

---

## 적용 전략

모든 페이지에 일괄 적용하지 않고,
**필요한 페이지만 Custom Hook + 컴포넌트 분해 패턴을 시범 적용**한다.

이를 통해:

- 구조의 타당성 검증
- 과도한 추상화 여부 판단
- 실제 유지보수 비용 측정

을 먼저 진행한다.
